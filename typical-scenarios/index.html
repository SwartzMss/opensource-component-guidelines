    典型场景案例¶

    文档目的¶

    本篇通过几个常见场景，说明开源组件治理在实际工作中该如何判断，而不是只停留在概念层面。

    这些案例强调的是判断思路，不替代正式法务结论。

    场景一：后端服务内部使用 MIT 组件¶

    场景描述¶

    团队要在内部后端服务中引入一个 MIT License 的工具库，仅部署在公司自有环境中，不对外分发安装包，也不向客户交付源码。

    常见判断¶

    • 一般属于低风险场景
    • 通常可以使用
    • 仍然应该记录组件名称、版本、来源和 License

    需要注意的点¶

    • 不要因为“只是内部使用”就完全不做留痕
    • 后续如果该服务被打包成交付物，义务边界可能会变化
    • 升级版本时仍要重新检查 License 和漏洞情况

    场景二：客户端产品集成 Apache-2.0 组件¶

    场景描述¶

    团队开发一个会交付给客户安装的客户端产品，其中集成了 Apache-2.0 License 的第三方组件。

    常见判断¶

    • 一般可以商用和分发
    • 通常对闭源集成相对友好
    • 但分发时不能忽略声明义务

    需要注意的点¶

    • 要保留必要的版权声明和 License 文本
    • 如果组件要求关注 NOTICE 文件，也应同步检查
    • 需要把相关信息纳入发布前检查流程

    场景三：复制第三方 GitHub 代码片段到自己项目¶

    场景描述¶

    工程师从某个 GitHub 仓库复制了一段工具代码，直接放进业务仓库中做了少量修改，但没有保留原始说明。

    常见判断¶

    • 这是高频且容易被忽略的风险场景
    • 不能默认 GitHub 上的代码就一定可以任意复制
    • 即使组件没有通过包管理器引入，也仍然可能受 License 约束

    需要注意的点¶

    • 先确认该仓库是否明确声明 License
    • 如果没有 License，默认不应随意复制使用
    • 如果已复制并修改，应补齐来源、版权声明和修改留痕

    场景四：闭源产品中使用 LGPL 库¶

    场景描述¶

    一个桌面或服务端产品计划接入 LGPL License 的库，主产品本身希望保持闭源。

    常见判断¶

    • 不能直接按 MIT 或 Apache-2.0 的思路处理
    • 是否可接受，通常与接入方式和修改范围有关
    • 应进入中高风险审查

    需要注意的点¶

    • 是否修改了 LGPL 组件本身
    • 如何进行链接和交付
    • 分发时是否需要满足额外义务

    场景五：SaaS 服务端使用 AGPL 组件¶

    场景描述¶

    团队计划在 SaaS 平台中使用 AGPL License 的服务端组件，软件不以安装包形式交付，但会对外提供在线服务。

    常见判断¶

    • 这是应重点关注的高风险场景
    • 不能因为“不发安装包”就认为没有开源义务
    • 应默认进入人工审核流程

    需要注意的点¶

    • AGPL 在网络服务场景下的影响比普通 GPL 更敏感
    • 需要评估是否会触发源码提供相关义务
    • 没有明确审查结论前，不应直接投入正式商用环境

    场景六：组件升级后 License 发生变化¶

    场景描述¶

    一个原本长期使用的组件，在新版本中调整了 License，或者改成双 License 模式。

    常见判断¶

    • 组件升级不只是技术问题，也是合规问题
    • 不能因为旧版本可用，就默认新版本同样可用

    需要注意的点¶

    • 升级前重新核对正式 License 声明
    • 评估新旧版本在分发义务和闭源边界上的变化
    • 如有争议，保留在旧版本并发起专项评估

    从案例中提炼的判断路径¶

    面对一个具体组件时，可以按这个顺序快速思考：

    1. 它的正式 License 是什么
    2. 我是内部使用、对外交付，还是网络服务
    3. 我有没有修改它，或者复制它的源码
    4. 它会不会进入闭源产品
    5. 分发时我要附带哪些声明和文本
