    开源组件使用规范¶

    文档目的¶

    本篇说明团队在引入、使用、升级和替换开源组件时应遵循的基本原则。

    核心目标有两个：

    • 降低工程风险
    • 降低 License 与合规风险

    为什么不能随意使用开源组件¶

    开源组件虽然可以公开获取，但并不代表可以无条件、无边界地使用。

    不规范使用通常会带来以下问题：

    • 引入存在安全漏洞或长期无人维护的依赖
    • 引入与业务场景不兼容的 License
    • 在分发产品时遗漏版权声明和 License 文本
    • 在不了解 Copyleft 要求的情况下进行闭源集成
    • 因依赖来源不清晰导致后续无法审计和整改

    基本原则¶

    1. 先评估，再引入¶

    在引入任何开源组件之前，至少应评估以下内容：

    • 组件用途是否明确
    • 是否真的有引入必要，能否复用现有能力
    • 社区活跃度和维护状态是否健康
    • 是否存在已知严重漏洞
    • License 是否与当前产品形态兼容

    2. 来源可追溯¶

    每个引入的开源组件都应该能追溯到：

    • 官方仓库地址
    • 版本号
    • License 类型
    • 引入时间
    • 使用场景
    • 责任人或维护人

    3. 版本要可控¶

    不建议无约束地依赖 latest 或不透明的动态版本。

    应尽量做到：

    • 固定明确版本
    • 记录升级原因
    • 评估升级带来的功能、兼容性和 License 变化
    • 在高风险场景下保留升级审查记录

    4. 使用方式要与 License 匹配¶

    不同 License 对以下行为的要求不同：

    • 使用
    • 复制
    • 修改
    • 分发
    • 再授权
    • 闭源集成

    因此不能只看“开源”两个字就默认可以任意商用或闭源。

    5. 发布前必须做合规检查¶

    如果软件会对外发布、交付或分发，应在发布前确认：

    • 依赖清单完整
    • License 信息完整
    • 需要保留的版权声明已保留
    • 需要附带的 License 文本已附带
    • 高风险 License 已完成审查

    推荐的管理动作¶

    组件引入阶段¶

    • 填写引入目的
    • 确认版本和来源
    • 识别 License 类型
    • 评估是否存在替代方案

    研发使用阶段¶

    • 避免私自替换为来源不明的 fork 版本
    • 避免拷贝第三方源码后不保留原始声明
    • 对本地修改过的第三方代码做标记和记录

    升级维护阶段¶

    • 定期关注安全漏洞和停止维护风险
    • 升级时检查 License 是否变化
    • 重大版本升级前进行兼容性评估

    下线替换阶段¶

    • 对历史依赖保留审计记录
    • 若存在遗留源码拷贝，确认是否仍在产物中分发

    不推荐的做法¶

    • 只因为“能跑起来”就直接引入组件
    • 从不明网站下载源码或二进制包
    • 不记录组件版本和来源
    • 误把示例代码、脚本片段当作无 License 限制内容
    • 修改开源代码后删除原始版权声明

    落地建议¶

    如果这个仓库后续要面向团队内部长期使用，建议继续补充以下内容：

    • 组件准入标准
    • 组件黑白名单机制
    • 高风险 License 审批规则
    • 发布物 License 附带模板
    • 依赖台账模板
