# 常见 License 对比表

## 文档目的

本篇用于提供一个面向工程实践的快速对比视图，帮助团队在选型和审查时先做初步判断。

这张表强调的是治理视角下的常见理解，不替代正式法律判断。

## 快速对比

| License | 类型 | 允许商用 | 允许修改 | 闭源集成友好度 | 分发时常见义务 | 风险提示 |
| --- | --- | --- | --- | --- | --- | --- |
| MIT | 宽松型 | 是 | 是 | 高 | 保留版权声明和 License 文本 | 整体较友好，但不能遗漏声明 |
| BSD-2-Clause / BSD-3-Clause | 宽松型 | 是 | 是 | 高 | 保留声明，部分版本有限制宣传条款 | 与 MIT 接近，需看具体版本 |
| Apache-2.0 | 宽松型 | 是 | 是 | 高 | 保留声明，关注 NOTICE 和专利条款 | 商业场景常见，专利条款需理解 |
| LGPL | 弱 Copyleft | 通常可以 | 是 | 中 | 修改库本身时通常需开放相关部分 | 需结合链接方式和交付方式判断 |
| MPL-2.0 | 弱 Copyleft | 通常可以 | 是 | 中 | 修改过的 MPL 文件通常需继续开放 | 文件级要求，不能按 MIT 处理 |
| GPL-2.0 / GPL-3.0 | 强 Copyleft | 可以，但需谨慎 | 是 | 低 | 分发时可能触发更强源码开放义务 | 不适合未经审批直接进入闭源产品 |
| AGPL-3.0 | 强 Copyleft | 可以，但风险更高 | 是 | 低 | 网络服务场景也可能触发源码提供义务 | SaaS 场景必须重点审查 |

## 如何使用这张表

建议把这张表当作第一层筛查工具，而不是最终结论。

可以按下面方式使用：

1. 先确认组件实际采用的 License
2. 再看它属于宽松型、弱 Copyleft 还是强 Copyleft
3. 然后结合自己的使用方式判断风险
4. 如果涉及分发、闭源交付、源码修改或网络服务，再进入更细致审查

## 容易误判的点

### 商用不等于无条件闭源

很多 License 允许商用，但这不代表分发时没有义务，也不代表修改后可以不保留声明。

### 同属 Copyleft，影响范围也不同

`LGPL`、`MPL`、`GPL`、`AGPL` 都不是宽松型 License，但它们约束范围并不一样，不能一概而论。

### 仓库描述不等于正式 License

最终判断应以仓库中的 `LICENSE` 文件、头部声明、发布包声明和官方说明为准。

## 使用建议

- 日常通用依赖优先考虑宽松型 License
- 对弱 Copyleft License 组件，要结合技术接入方式做判断
- 对 GPL、AGPL 类 License，建议默认进入人工审核流程
- 组件升级时重新核对 License，不要默认新旧版本完全一致
