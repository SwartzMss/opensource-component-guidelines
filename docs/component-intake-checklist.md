# 开源组件引入检查清单

## 文档目的

本篇提供一个可以直接使用的引入检查清单，帮助团队把开源组件使用规范落实到日常工作中。

## 使用方式

适合在以下时点使用：

- 新组件选型时
- 新依赖接入前
- 对第三方源码做复制或引入前
- 高风险依赖升级前

## 基础信息检查

- [ ] 组件名称明确
- [ ] 使用版本明确
- [ ] 官方仓库或官方来源明确
- [ ] 下载来源可信
- [ ] 组件用途明确
- [ ] 责任人明确

## 工程可用性检查

- [ ] 社区仍在维护
- [ ] 最近版本更新节奏正常
- [ ] 文档相对完整
- [ ] 与当前技术栈兼容
- [ ] 引入后不会显著增加复杂依赖链
- [ ] 存在可接受的替代方案评估结果

## 安全风险检查

- [ ] 已检查是否存在公开高危漏洞
- [ ] 已关注供应链投毒或来源异常风险
- [ ] 依赖包发布者和仓库关系基本可信
- [ ] 不依赖明显过期或无人维护版本

## License 检查

- [ ] 已识别 License 类型
- [ ] 已确认 License 信息来自正式声明而不是仓库简介
- [ ] 已判断是否允许当前使用方式
- [ ] 已判断是否允许商用
- [ ] 已判断是否允许闭源分发
- [ ] 已判断是否存在源码开放义务
- [ ] 已判断是否需要附带版权声明或 License 文本

## 使用方式检查

- [ ] 当前是仅内部使用，还是会对外分发
- [ ] 是否会把该组件嵌入商业产品
- [ ] 是否会修改第三方源码
- [ ] 是否会复制第三方代码到本仓库
- [ ] 是否涉及 SDK、镜像、安装包或客户端交付
- [ ] 是否涉及网络服务场景

## 高风险判断

以下任一项命中时，建议进入人工审查：

- [ ] License 为 GPL、AGPL 或其他强 Copyleft 类型
- [ ] License 为双 License 或条款复杂，难以直接判断
- [ ] 组件来源不清晰
- [ ] 项目中需要修改并再分发第三方源码
- [ ] 组件将进入闭源商业交付物
- [ ] 组件可能涉及专利风险

## 接入留痕检查

- [ ] 已记录组件名称、版本、来源和 License
- [ ] 已记录使用模块和使用目的
- [ ] 已记录引入时间
- [ ] 已记录责任人
- [ ] 如有本地修改，已记录修改内容

## 发布前附加检查

如果组件会进入对外发布物，还应继续确认：

- [ ] 发布物中的第三方依赖清单完整
- [ ] 所需版权声明已保留
- [ ] 所需 License 文本已附带
- [ ] 高风险 License 已完成审核
- [ ] 发布说明或第三方声明文件已准备

## 最低准入建议

如果团队当前流程还不成熟，至少满足下面四条再引入：

1. 来源清晰
2. 版本清晰
3. License 清晰
4. 使用边界清晰
