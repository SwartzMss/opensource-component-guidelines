# 开源合规流程

## 文档目的

本篇提供一个适合团队落地的基础合规流程，帮助把“知道规则”变成“能执行的动作”。

## 适用场景

适用于以下常见场景：

- 新引入第三方开源组件
- 升级现有依赖
- 复制或修改第三方源码
- 发布包含开源依赖的产品
- 对外提供软件交付物或服务

## 基础流程

### 1. 需求提出

在决定引入组件时，先明确：

- 解决什么问题
- 为什么要引入外部组件
- 是否存在内部能力或更低风险替代方案

### 2. 组件识别

记录组件的基础信息：

- 名称
- 版本
- 来源仓库
- 官方下载地址
- License 类型
- 使用方式

### 3. 风险初筛

从三个角度做快速判断：

- 工程风险：维护状态、兼容性、依赖复杂度
- 安全风险：已知漏洞、供应链风险
- 合规风险：License 类型、分发义务、是否涉及 Copyleft

### 4. 准入判断

可以按风险级别做简单分类：

- 低风险：宽松型 License，常规依赖，引入记录完整
- 中风险：需要补充声明、审查分发方式或核实修改范围
- 高风险：GPL、AGPL、复杂双 License、来源不清或存在专利疑点

高风险场景不应由研发自行拍板，应进入更正式的审批流程。

### 5. 使用与留痕

组件正式使用后，应保留以下记录：

- 引入记录
- 使用模块
- 责任人
- 修改记录
- 发布影响范围

### 6. 发布前检查

在对外发布、交付或上线前，至少检查：

- 依赖清单是否完整
- 组件 License 是否识别准确
- 是否附带所需声明和 License 文本
- 是否存在未审查的高风险依赖
- 是否包含拷贝进项目的第三方源码

### 7. 运行期维护

合规不是一次性动作，还需要持续维护：

- 跟踪组件漏洞
- 跟踪停止维护风险
- 跟踪 License 变化
- 跟踪 fork 和本地修改情况

## 推荐产出物

如果团队要把流程落地，建议逐步补齐以下产物：

- 开源组件台账
- 依赖引入申请模板
- License 风险分级表
- 发布前检查清单
- 第三方声明文件模板

其中，“开源组件引入检查清单”可以先作为最低成本落地物优先使用：

- [开源组件引入检查清单](component-intake-checklist.md)

## 最低可执行版本

如果当前团队还没有完整治理体系，至少先做到下面这些：

1. 所有引入组件都记录名称、版本、来源和 License
2. 所有对外发布的软件都补齐第三方 License 声明
3. GPL、AGPL 等高风险 License 必须人工审核
4. 修改过的第三方源码必须留痕

## 后续增强方向

- 对接自动化依赖扫描工具
- 生成 SBOM
- 建立开源准入白名单和黑名单
- 将发布前检查接入 CI/CD 流程
