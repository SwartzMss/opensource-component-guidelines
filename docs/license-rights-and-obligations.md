# License 权限与义务

## 文档目的

本篇聚焦一个实际问题：面对某个开源组件的 License，团队最关心的到底是什么。

通常不是去背法律文本，而是要快速回答下面几个问题：

- 能不能用
- 能不能商用
- 能不能改
- 能不能闭源
- 能不能分发
- 分发时要附带什么

## 常见关注维度

### 1. 使用权限

通常要区分：

- 内部使用
- 商业使用
- 嵌入产品使用
- 对外分发使用

很多 License 对“内部使用”相对宽松，但一旦进入“对外分发”或“嵌入产品交付”，义务就会明显增加。

### 2. 修改权限

需要确认：

- 是否允许修改源码
- 修改后是否必须公开修改内容
- 修改后的文件是否必须沿用相同 License

### 3. 分发义务

如果把包含开源组件的软件交付给客户、合作方或公众，通常要关注：

- 是否需要附带原始 License 文本
- 是否需要保留版权声明
- 是否需要标明已做修改
- 是否需要提供源码或可获取源码的方式

### 4. 闭源边界

团队最容易误判的是“能商用”不等于“能闭源分发且没有附加义务”。

需要重点看：

- License 是否允许与闭源代码组合
- 组合方式会不会触发更强义务
- 修改第三方代码后是否需要开放修改部分

### 5. 专利相关条款

有些 License 不只涉及版权，也涉及专利授权或专利终止机制。

这在以下场景尤其重要：

- 基础框架
- 通信协议实现
- 编解码相关组件
- 涉及专利密集领域的算法实现

## 用工程语言理解几类典型差异

### MIT / BSD

一般可理解为：

- 使用自由度高
- 商业友好
- 通常允许闭源集成
- 但仍需保留声明

### Apache-2.0

一般可理解为：

- 也较宽松
- 对专利条款表达更完整
- 适合希望边界更明确的商业场景

### LGPL / MPL

一般可理解为：

- 不是完全宽松
- 需要看修改范围和集成方式
- 不能简单按 MIT 的思路处理

### GPL / AGPL

一般可理解为：

- 风险高于宽松型 License
- 对闭源交付和网络服务场景更敏感
- 使用前应进入正式评估流程

## 实操中的最低要求

无论使用哪类 License，至少应做到：

- 识别组件 License 类型
- 保存 License 原文
- 保留必要版权声明
- 记录是否对第三方代码做过修改
- 在发布前核对分发义务是否满足

## 不应直接下结论的说法

以下说法在工程实践里都过于粗糙：

- 开源的就能随便商用
- 能商用就肯定能闭源
- 只要不改源码就一定没问题
- 只要项目在 GitHub 上就一定是开源可用
- 仓库没有写 License 也默认可以用

## 结论

License 管理的关键不是记住所有法律术语，而是建立稳定判断路径：

1. 先识别 License
2. 再判断使用场景
3. 然后确认义务
4. 最后决定是否准入、是否可发布
